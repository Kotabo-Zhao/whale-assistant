## 已核对的仓库事实

- `src/App.tsx` 在改动前为 297074 字节。改动后为 297731 字节。首屏组件变少，源文件没有变小，不能把文件体积当成体验改进。
- 应用 `abiFilters` 只有 `arm64-v8a`。
- `harness-web` 是子模块，指针 `abefc709ebdd4aada322cde573f2684327bd661b`。云端工作区起初没有检出该目录，契约测试因此有 3 项因缺少 `harness-web/package.json` 失败。检出指针之后这 3 项通过。

- 已有 Worker、工单、预算和监督实现。本阶段没有新造第二套 Super Agent。

## 模拟器

云端机器是 x86_64，`/dev/kvm` 存在。进程用户起初不能读这个设备（`crw-rw---- root:kvm`）。用 sudo 把设备改为可读写后，当前用户可以打开它。这只说明宿主暴露了 KVM，不说明 arm64 客户机能用它加速。

已安装 Android 命令行工具、platform 35、build-tools、模拟器 37.2.13.0，以及系统镜像 `system-images;android-35;google_apis;arm64-v8a`。创建 AVD `whale-arm64` 后启动失败，模拟器原文：

```
FATAL | Avd's CPU Architecture 'arm64' is not supported by the QEMU2 emulator on x86_64 host. System image must match the host architecture.
```

因此没有启动 x86_64 镜像来代替验收。x86_64 壳即使能进系统，也装不上只含 `arm64-v8a` 的安装包，更不能运行其中的 PRoot 与 Node。PRoot、对话服务、Shizuku、无障碍和桌宠悬浮层都仍是真机项目。没有模拟器耗电数据，也不能用来代表 AYANEO。

## 这一阶段改了什么

1. 底部和侧栏主导航只保留「对话」和「我的」。资料、任务、工具从对话页的三个入口进入，也从「我的 → 日常」进入。设备控制、运行环境、诊断仍在「高级设置」。
2. 对话就绪页不再同时铺开概览、示例任务和内嵌会话列表。会话仍从顶栏进入，任务和工具仍可从入口进入。空闲文案仍是「对话已就绪 / 点击打开对话开始」，没有把空闲写成正在打开。自动启动、凭据闸门、更新确认和忙锁没有改。
3. GitHub / 飞书设置挂到诊断页里原有的折叠面板。默认不展开，展开后才按原来的 5 秒间隔读取。没有新增对话页轮询，也没有做跨渠道收发。
4. 偏好里还没有写过的 `bubble_memory_access`、`knowledge_model_access` 缺键时读为开启。已经写成 `false` 的保持关闭。通知正文、日历、资料写入、完全权限的缺键默认仍是关闭。
5. 事项查询不再因为通知访问关闭就拒绝秘书事项。结果里的 `omittedSources` 写明被省略的来源。更新某一条事项时仍按该条来源检查授权。删除、改期和状态变更沿用原来的冲突校验，没有改成静默成功。

## 迁移与兼容

- 不迁移、不删除记忆、资料、事项、会话或插件数据。
- 缺键与显式 `false` 不是同一件事。升级后，从未拨过这两个开关的安装会开始允许桌宠使用长期记忆，以及允许对话检索本地资料。检索到的内容仍可能发给当前模型服务。用户可在「我的 → 桌宠与主动跟进 → 助手偏好」关掉。
- 关掉资料检索时，原有逻辑仍会关闭语义索引。这是既有关闭路径，不是这次新增的删除。
- 旧版回读缺键时会把上述两项当成关闭。只回退安装包、不改偏好文件时，行为会回到「缺键即关闭」。已经写成 `true` 或 `false` 的值两边都按原值读。

## 第二阶段：就绪后直接进入会话（2026-11-16）

凭据、运行环境都就绪，且没有待确认更新、没有「需要重新连接」时，栈底从门屏换成 `#harness`。手机上沿用原来的内嵌 WebView：进入这个标签会启动并打开会话，视口仍只盖住主内容区，外壳导航留在外面。浏览器预览不调用 `startHarness` / `openHarness`，只显示同一块区域，并写明手机上会由内嵌会话盖住。

仍会停在说明页的情况：没有模型凭据、运行环境未安装或正在下载、有待确认的运行环境更新、启动失败、后台记录要求重新连接。失败后不会自动连着重试，门屏上的按钮可以再试一次。预启动仍然只调用 `startHarness`；打开会话时如果预启动还在进行，会等它，不会再发一次启动。

### CI

拉取请求上的这次检查（run `43926926183`，提交 `e1b0057a`）：

| 作业 | 结果 |
| --- | --- |
| Quality gates | 通过 |
| Build PRoot runners | 失败。运行器已经编出来，上传制品时 GitHub 返回 `Artifact storage quota has been hit` |
| Build embedded runtime bundle | 失败。同样是制品配额，失败点在上传 `runtime-legal` |
| build / Publish release | 跳过，因为上面两个作业失败 |

这不是本次源码引入的编译错误。配额是仓库的 Actions 存储限制，不能靠改工作流绕过。因此 CI 没有产出带 `rootfs.bundle` 和 `libdsh_proot.so` 的安装包。

标准打包顺序写在 `.github/workflows/android-build.yml`：先编 arm64 PRoot 运行器并上传 `proot-runners-arm64`，再编 Ubuntu rootfs 并上传 `embedded-runtime`，最后由 `build` 作业下载这两份制品，把 `rootfs.bundle` 与 `runtime-manifest.json` 放进 `android/app/src/main/assets/runtime/`，把两个 `.so` 放进 `jniLibs/arm64-v8a`，再打 APK。仓库里不提交这些大文件。本机没有运行器，也没有 rootfs，所以不能在这里打出可启动 PRoot 的完整包。上一阶段的调试包仍然只是壳，不能当作这一阶段的交付。

ARM64 模拟器在 x86_64 宿主上无法启动，这一阶段没有再试。也没有为了看壳布局再下载 x86 系统镜像；主要时间用在会话页。
