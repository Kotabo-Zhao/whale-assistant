# AYANEO 异常模拟与容灾设计

2026 年 11 月 6 日，Pocket S。前半部分保留 preview.71 的故障发现与方案，文末记录 preview.72 / 运行环境 0.3.72-whale-resilience 已完成的修复与复测。按用户安排，本轮继续验证本地能力，真实跨渠道测试另行安排。

**已落地的第一层监督。** Android 定时线程、监督模型 HTTP 请求与 Node 执行循环分开运行。运行中的工单保留运行代次、心跳、观察序号、工具结果指纹及重试期限。只有证据对应的原工单仍在执行、权限仍有效、运行代次和观察序号仍一致时，监督结果才可请求暂停。新输入尚未被读取、已经取得新进展、进入新运行代次或提交最终报告时，旧判断失效。设备任务还核对设备租约的运行代次。

**存储故障带来的新缺口。** 生产任务队列按文件保存，目标账本与领域快照也使用 JSON。完整临时文件发布前中断，可以保留原来已发布的记录；但已发布的一个工单 JSON 损坏，会使整批任务队列加载失败。目标 JSON 损坏会阻断目标账本初始化，原生监督日志损坏也会阻断该次检查。这些场景在新建私有目录中复现，真实用户资料与工单没有被改写。复现成功表示已确认影响范围，恢复与隔离机制仍需按下述方案落地。

另用一个临时路径被目录占用的场景模拟写入失败。旧磁盘记录仍可读取，但当前保存函数已经提前推进内存里的序号，内存与磁盘出现差异。这个测试覆盖实际文件写入失败，不据此推断整块存储写满或突然断电后的表现。

**拟采用的故障边界。** 每个事件都进入一张本机恢复记录，记录故障类型、受影响工单、运行代次、已验证副本、恢复尝试次数、下一次尝试时间及需要用户确认的内容。记录只包含必要的标识与状态，密钥沿用加密凭据存储。

| 级别 | 范围 | 处理与恢复条件 |
| --- | --- | --- |
| 单次请求异常 | 超时、限流、临时断网 | 保留原请求 ID 和用量，按退避期限重试。正常重试期内不判定任务停滞；连续失败达到上限后交给用户。 |
| 单个工单异常 | 重复空转、权限撤回、某个执行器中断 | 暂停该工单及依赖它的后续步骤，独立工单继续。恢复前核对来源权限、当前要求与是否发生过副作用。 |
| 单份记录损坏 | 工单、目标或监督元数据校验失败 | 保存坏文件供诊断，隔离对应记录，展示可验证的只读镜像。损坏记录保持待核对，相关写入和后续任务冻结；健康记录应能继续加载。 |
| 运行环境异常 | Node / PRoot 卡死或启动失败 | 由 Android 侧检查，依据进程身份与启动时间处理本应用的进程。重建运行环境后，只读任务回到原工单；操作及创作先核对现场。用户手动停止时等待下一次启动指令。 |
| 设备级异常 | 整机重启、存储不足、应用被系统回收 | 根据持久运行意图和用户的后台设置恢复服务，先检查存储与日志完整性。Android 强制停止后的恢复入口是用户再次打开 App。完整熄屏、整机重启和低空间实测仍待执行。 |

**状态落盘方案。** 建议把领域状态、工单输入、运行代次、目标核验、回执队列和恢复记录收敛到一个 SQLite 数据库，使用 WAL 与明确的迁移版本；对话正文、图片和大附件继续作为文件保存，由数据库记录版本及校验值。一次事务同时提交状态变化和待执行动作，动作在提交成功后开始。写入失败时，内存对象也保持在上次已提交的版本。现有 JSON 可作为导出与只读兼容入口，迁移须先保留完整快照并验证。

关键约束如下。

- 输入以稳定 actionId 去重，执行以 runId 和授权代次区分，恢复不会生成新的用户授权。
- 已开始发送却没有确认的动作进入 unknown。先查询目标回执或核对现场，再决定补发。GitHub 现有消息标记和飞书现有稳定 UUID 可继续用于查询及去重，真实账号链路另行验收。
- 记录损坏后恢复的副本只供核对。旧授权、旧完成结论及较低的预算用量均不能直接恢复为可执行状态。
- 相互依赖的任务按证据版本推进。上游结果更正后，下游旧核验失效，重新计算受影响部分并保留核验历史。
- 监督元数据损坏时先隔离坏副本，暂停新的模型检查额度，保留原工单和已有命令；恢复检查记录后再开始新的判断，避免重置计数导致重复打扰。
- 每次自动恢复都有有限次数和退避期限。建议首版只读任务最多自动恢复两次，之后显示原工单、已知进展及人工接管入口；涉及点按、发送、安装或写入时先确认已经执行到哪一步。

**下一轮落地与验收顺序。** 先修复单记录损坏导致整批加载失败，以及保存失败后内存版本提前推进。其次实现带完整性校验的恢复记录与只读副本入口。之后再迁移事务存储，逐步加入磁盘写满、写入中杀进程、迁移中断、整机重启及长时熄屏测试。每一项都要求健康工单继续可用，异常工单可解释，权限和用量可追溯，副作用保持待核对。


**构建与记录。** 本轮前端 1,153 项、脚本 465 项通过（4 项跳过），Android 单元共 1,844 项，失败和错误均为 0（37 项跳过）。隔离故障实验类三项在 Pocket S 的实际运行环境中完成，模拟记录见 build/p71-verified-disaster-device.log；真实运行测试日志均在表中列出。故障实验的“通过”表示复现结果符合断言，其中存储损坏所暴露的缺陷仍在。

本轮还修复了一处监督退避问题：如果旧暂停请求因新进展而失效，同一运行代次后续的新证据仍应能再次触发检查。去重现在同时核对证据序号，单份证据继续只处理一次。私有日志实验覆盖了这个恢复条件。


## 第二轮：存储隔离与恢复已落地

工单保存改为临时文件发布，并维护带 SHA-256 校验的独立副本。正常启动为旧工单补一次副本；未变化记录不会反复写盘。损坏 JSON、可解析但字段类型错误、主记录缺失均进入单记录恢复分支，原始坏文件保留到诊断目录。正常工单仍可加载。

恢复副本始终先进入待核对状态。旧回执暂停投递，旧完成结论不直接回到目标核验；恢复预览会保留原请求、结果和已记录用量。没有完整校验副本时，原生旧镜像只供参考，不能解锁执行。副本中不存在的新目标也不能通过默认预算解锁。

App 与桌宠任务详情提供核对入口，确认携带当前事故标识；副本变化后旧确认无效。解锁只解除恢复标记，用户仍需补充说明并单独继续原工单。保存失败会回滚同一个内存对象及版本，目标定义也回到最近一次提交。监督日志损坏后保留异常文件、恢复可校验元数据，并暂停新模型检查一小时；基础运行状态检查仍可用。
