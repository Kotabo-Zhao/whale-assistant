## 对照 DeepSeek 的五个架构模块

比较采用两层依据。DeepSeek Harness 团队的设计文章定义了五个模块；其公开仓库实现了面向单个 GitHub 仓库的研究原型，并明确说明它与内部系统、文章设想有差别。下表以文章为能力目标，以公开代码为机制参照，以鲸鱼的源代码与 Pocket S 记录判定进度。[团队设计文章](https://x.com/DeepSeekHarness/status/2116857257245987236) · [公开原型说明](https://github.com/deepseek-ai/dsh-superagent-prototype) · [原型架构与状态机](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/007-architecture.md)

| 架构模块 | 鲸鱼已经做到 | 剩余缺口与验收方法 |
| --- | --- | --- |
| **1. 两层协调与执行**：协调者处理用户意图，Worker 独立执行 | 工单、独立会话、追问、权限委派、目标预算均已接入。两项真实任务能由原协调会话独立核验；另开聊天不会抢走负责人。 | **复杂协调待验。** 给三个有依赖的工单安排矛盾结果，执行中修改目标或撤销其中一项。检查协调者能否找出冲突、作废旧证据、只重派受影响部分，并给出可追溯结论。 |
| **2. 事件驱动**：收集事件，判断是否值得行动，把后续信息交给原任务 | 本地对话和资料更新已跑通主动判断与去重。领域层有触发事件、线程订阅、裁决、工单关联和越界事件退回。 | **本地样例已验，持续判断质量待量化。** 用一组已标注的真实风格事件混合测试重复、乱序、无关噪声、事项实质变化和权限撤回；统计误提醒、漏跟进及重复打扰。外部事件积压与重放另需联测。 |
| **3. 双向异步、多渠道交互**：后台工作时能继续交谈，换入口仍认得原事 | 桌宠能连续交办，后台等待不占住其他任务。App、桌宠共享工单和收件箱；GitHub、飞书已有适配和授权机制。 | **缺真实账号闭环。** 用授权测试账号从飞书发起任务，在 GitHub 改要求或关闭 PR，再回到原对话检查结果。验收同一工单、身份重新校验、断线补送和一次回执，也要验证无权限的人无法中途接管。 |
| **4. 计算、状态与执行环境分离** | 工单、输入、回执和预算可落盘；Worker 会话独立，创作工单有专属工作目录。已在掌机生成待审 HTML 草稿，用户可在桌宠里使用已启用工具。 | **隔离与交付仍局部。** 专属目录并不证明所有工具都受文件系统沙箱约束。应测越界读写、异常退出后目录归属、产物版本冲突，以及原生 APK 的构建、独立测试、人工评审、应用和回退。按既定产品范围，任务数据留在本机，跨设备同步不列入待办。 |
| **5. 独立监督与恢复（Watchdog）**：主系统出故障或任务偏离目标时，另有机制介入 | 已有运行时监督、心跳、用量及重试记录，原工单的跨进程恢复已实测。最终版修复了重复建会话、丢失来源工具和预算检查覆盖最终回执。 | **当前最大可靠性缺口。** 尚无完整证据表明独立于主执行循环的监督者能发现“进程还活着、任务已无进展”，并选择重试、暂停或交给用户。须分别测试断网、反复空转、长时熄屏、系统回收和整机重启，核对恢复点、预算与副作用。涉及点按、发送和安装的任务，恢复时应重新核对授权及动作是否已经执行。 |

公开原型的接单链可以沿“来源事件 → 线程 → 判断与授权 → 工单 → 执行与输入 → 回执队列”追踪。鲸鱼已经有这些核心对象，因此判断架构差距时，最有价值的测试是故障跨过两个环节时是否仍一致。例如，外部消息已经送达、本地回执尚未来得及落盘就断线，重连后能否避免再次回复。[上游事务、执行与回执机制](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/007-architecture.md)

## 商用性能与成本

Pocket S 连续切换标签 15 次，171 帧中有 3 帧超时，第 95 百分位为 16 ms。对话页静置 5 分钟，计入 App、Node、PRoot 和隔离 WebView 渲染器，PSS 中位数 691.6 MiB、峰值 851.3 MiB，CPU 中位数为单核的 4.86%。这些数据可以作为下一版的同负载基线。旧版负载和进程覆盖不同，无法从两轮数据推导整体降耗比例。[Pocket S 性能记录](整合开发与PocketS验收-20261105.md)

Token 成本也影响可持续使用。一次真实 HTML 创作累计 44,373 tokens，一次跨进程两文件恢复用例累计 79,397 tokens。预算按模型回传的多轮用量入账，单次调用仍可能越过剩余额度。商用验收还需要长时离电测试、不同并发数下的内存峰值，以及按任务类型统计成功率、延迟和用量。[执行与预算实测](整合开发与PocketS验收-20261105.md)

## 建议的下一轮顺序

1. **先做独立监督和故障注入。** 让一个 Worker 故意无进展、让另一个正常工作。通过条件是前者能被识别并安全移交，后者能完成，重启后没有重复动作或丢失回执。
2. **再用一个真实跨渠道任务验收整条链。** 从飞书提出需求，在 GitHub 修改要求并合并，结果回到原对话。沿同一工单核对身份、规则、执行和投递记录。
3. **最后把产物验收和成本做扎实。** 选一个有冲突证据的多工单目标和一个原生工具，分别检验重规划与交付回退；同步记录完成质量、人为干预次数、用时、用量和耗电。
