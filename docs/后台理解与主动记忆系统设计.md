# 鲸鱼娘后台理解、长期记忆与主动助理设计

日期：2026-10-30。状态：设计，尚未实现。本轮不继续之前已清除的持续开发目标，不修改已有未提交代码。

## 1. 产品目标

让助手在授权范围内持续整理手机信息，理解事情之间的关系，识别变化、截止时间和可能需要处理的事项，并主动提供有依据、可纠正、不过度打扰的提醒与建议。用户不需要逐条确认普通记忆。

当前 CompanionMemoryStore 使用有固定容量约束的 JSON 记录，自动通知/使用摘要主要由本地规则生成。下一代不是简单提高条数或调用模型给通知分类，而是引入事件库、语义记忆、事项状态机、后台推理队列和反馈闭环。

“理解”指模型对上下文进行提取、关联、归纳和规划建议，不代表持续意识或保证推断正确。“没有上限”指不设 100 条等产品级固定条数限制，仍受设备存储、计算和服务费用约束。

## 2. 整体链路

授权信息进入事件库 → 去重及敏感信息处理 → 低成本变化检测 → 小批量模型理解 → 关联已有记忆及事项 → 校验证据与时间 → 保存事实/推断/事项 → 决定是否提示 → 收集用户反馈 → 更新或撤回。

每个阶段独立记录状态和版本，失败可重试，不重复生成记忆或通知。Harness 对话与后台整理共用同一份记忆和事项库，不复制出“桌面宠物专用记忆”。后台文本理解不需要每次启动整个 Ubuntu/Harness；使用独立的模型客户端与现有凭据服务，模型设置保持一致。

## 3. 五层数据模型

| 层 | 内容与关键字段 | 用途 |
|---|---|---|
| 原始事件 | id、来源应用、来源对象标识、版本、内容哈希、发生/采集时间、时区、正文引用、授权范围、保留策略 | 保留来源，处理通知更新与重复 |
| 情景记忆 | 摘要、参与对象、事件时间范围、来源事件集合、生成模型/提示版本、有效期 | 理解“最近发生什么” |
| 语义记忆 | 事实/偏好/推断类型、主体、属性、值、证据、有效时间、置信档、冲突组、用户纠正版本 | 理解稳定信息与变化 |
| 事项 | 目标、相关对象、截止时间/时间范围、状态、行动建议、证据、提醒计划、去重标识 | 管理“有哪些事要处理” |
| 用户反馈 | 提醒是否有用、已完成、稍后、不再提醒、事实纠正、来源排除 | 校准策略与修订记忆 |

默认置信档使用明确/较可信/待核实，不把模型自报的 0.93 当作可靠概率。频率必须由原始事件统计得出，不能由模型凭印象生成。

实体关联采用规范化线索和证据：同名不自动认定同一人；跨应用弱匹配保留为候选关联。不要在数据库里无限扩展关系图，优先实现 SQLite 中可索引的实体与关联表。

## 4. 后台模型如何理解

### 4.1 增量提取

单次输入只含新变化、相关近期上下文和检索到的少量记忆，不发送整个手机档案。通知正文的完整性不确定时明确标记“可能截断”。

输出结构：事实候选、事项候选、对已有事项的修订、偏好候选、需要补充的信息、证据事件 ID。每个结论必须引用本次输入实际存在的证据；无证据引用、非法时间、未知对象或格式错误不能直接进入正式事项。

### 4.2 关联理解

对于“快递到站 → 又收到取件提醒”，合并同一事项并提高关注度，不生成两次提醒。对于“周五会议 → 改到下周一”，新证据更新截止时间并撤销旧提醒。对于“某订阅可能到期”，先判断是否确为用户订阅、时间是否明确；广告不能变成确定账单。

### 4.3 周期归纳

后台低频整理近期情景，提炼稳定偏好和未完成事项。一次点击或一次购买不足以断言长期偏好；反复出现并有可靠证据才形成较可信假设。涉及敏感属性的推断不因“信息齐全”就默认生成。

按时段批处理：普通信息可延后合并，明确临近截止事项优先。没有新增信息不重复调用模型。充电/网络/资源条件允许时才执行较重的归纳与索引维护。

## 5. 自动记忆与纠错

用户开启后台理解后，普通信息可自动进入情景记忆，明确事实可自动保存；推断单独标识，不要求逐条确认，也不伪装成用户亲口说过的话。只有重要歧义且确实影响行动时才提一个简短问题。

记忆状态：候选、有效、冲突、被替代、过期、用户否定。用户纠正具有最高优先级；模型不能在下一轮凭旧事件覆盖用户纠正。更新必须保留版本及出处，不对旧记录做不可追溯的覆盖。

删除提供两种明确语义：

- 只删除该记忆：原始事件保留，但写入删除抑制标识，禁止旧证据重新生成相同结论。
- 忘记这件事及相关来源内容：删除/去标识相关事件、摘要、索引及派生结论，撤销关联提醒；显示可能受影响的事项。

抑制标识使用规范化主题与证据版本，不保存被要求删除的正文；新事实是否可以重新生成由用户的“以后仍可学习”选择决定。恢复学习不是恢复已删除数据。备份恢复必须保留删除抑制与纠正版本，否则会把已忘记的内容带回来。

## 6. 主动提醒与建议

事项状态：观察中 → 待核实/可行动 → 已提醒 → 已完成/已取消/已过期；支持稍后提醒。通知被划掉不等于事项完成；应用使用行为也不能证明支付、回复或取件成功。

提醒策略综合考虑：时间紧迫性、用户相关性、证据可靠性、重复提醒次数、用户最近反馈和打扰成本。模型生成建议与解释，确定性的策略控制提醒频率、静默时段和渠道。

推荐初始策略：普通建议每日最多 2 次主动气泡；非紧迫事项并入简报；同一事项默认不重复打扰，除非时间临近或证据发生重要变化。用户可修改预算。明确用户设置的提醒独立调度，不受建议额度限制。

输出卡片必须包含：要提醒什么、为什么现在提醒、信息来自哪里、时间可信程度、完成/稍后/不相关/查看依据。重要事项发通知，其他内容以鲸鱼娘气泡为主；锁屏默认隐藏正文。

“建议回复某人”和“替用户发送消息”分开：后台理解可以主动建议，实际发送、删除、购买等仍遵循具体行动授权。信息中的命令只作为来源内容，不能变成助手系统指令或自行扩大权限。

## 7. 不设固定条数上限的存储设计

用 SQLite/Room 替代整文件 JSON，逐行更新、事务写入、索引查询和分页展示。正文较大时独立存储并由数据库引用。索引不是原始数据，损坏时可重建。

热数据：近期事件、活跃事项与常用记忆；温数据：已整理摘要及历史事项；冷数据：压缩归档原始内容。层级是访问策略，不是永久遗忘。检索先关键词、时间和实体过滤，再按需使用向量与重排序；向量索引可替换，不锁定某一家模型。

不设固定记忆数量上限，但必须提供空间仪表盘、剩余空间告警、索引/归档占用、导出和保留策略。低存储时优先暂停新采集或清理可重建缓存；未经用户策略授权，不静默删除长期记忆。每次推理有上下文和输出长度上限，这与记忆库容量无关。

检索返回片段而非全库；使用相关性、时效性、来源可信程度和用户纠正排序。过期事项可以作为历史回答，但不能继续触发当前提醒。

## 8. 后台执行与费用

后台队列持久化：作业 ID、事件范围、输入版本哈希、阶段、尝试次数、下次执行时间、模型版本、耗时/用量、失败码。事务中保存理解结果及通知待投递记录，投递也用幂等键；崩溃后重试不会重复提醒。

外部模型请求与数据库写入不能组成真正的单一事务，因此允许同一请求在不确定失败后重复计费，但必须去重落库及通知；尽可能使用服务支持的幂等机制，并在用量中记录不确定结果。

三个模式：省电（批量简报）、平衡（重要变化优先，其余批量）、积极（更频繁分析，明确更高耗电/费用）。默认平衡。用户可限制每天调用次数、token 或费用预算、移动网络使用和漫游；达到预算后保留待处理事件并显示延迟，不假装已理解。

本地规则只用于去重、减少无意义调用、时间与权限校验，不替代语义理解。模型不可用时已有明确提醒继续运行，新语义事项显示待分析。Android 可能延迟或终止后台执行，界面显示最近采集、理解、成功调度时间及积压量，不承诺永久在线。

模型部署支持云端、局域网与后续可选本机模式；不预设 Magic6 能以可接受速度运行指定模型。初期使用用户现有模型配置，后台和对话设并发优先级，避免整理抢占正在进行的对话。

## 9. 权限与数据流

来源限系统已授权的通知、使用统计、日历、用户分享/导入及授权可见内容；无 root 不代表能遍历其他应用私有数据库。不要为“全面理解”进行无限滚屏或持续截屏。

分别配置“可采集哪些应用”和“哪些内容可交给当前模型分析”。本地保存许可不自动等于云端发送许可。首次开启展示模型目的地、来源范围、后台频率与预算；之后普通处理不反复弹确认。来源撤权立即停止采集并取消尚未发送的相关作业；已经发到外部服务的数据不能承诺从对方服务器撤回。

凭据交给现有凭据服务，日志不包含正文与密钥。备份明确是否加密、是否包含原文、事件、删除抑制和索引；云备份与跨设备同步后续单独设计，不在首次版本默认启用。

## 10. 用户界面

设置只保留一级总开关“后台理解与主动建议”，下设来源范围、模型与预算、主动程度、记忆与隐私、运行状态。高级选项折叠，不把几十个规则开关平铺。

记忆页分“关于我 / 最近发生 / 待处理事项 / 历史”，每条可查看依据、修改、忘记和纠错。鲸鱼娘可回答“你为什么提醒我”“最近学到了什么”“这条记忆来自哪里”。回答引用本地证据，无法取得原文时只说明已有摘要。

首页显示需要注意的事项和最新简报；显示“已分析至何时”，避免让用户误以为未分析数据也已被考虑。

## 11. 迁移与实施

A. 数据基础：建立数据库、作业与事项表，旧 JSON 导入保留 ID/来源/时间/状态。迁移事务成功且校验计数后再切换读路径，旧文件留作回滚；旧 APK 不可直接读取新库，回退需使用配套导出或迁移前备份。

B. 后台理解：模型客户端、结构化输出校验、增量批次、来源授权、预算与重试。先用已知样例跑离线评估，再启用真实来源。

C. 主动事项：证据关联、改期/完成/取消识别、提醒去重与反馈界面。与现有提醒存储衔接，不新增第二个重复调度器。

D. 长期记忆：分层检索、纠错优先级、冲突与过期、删除派生链、归档和容量管理；规模测试后确定是否引入向量索引。

E. Harness/鲸鱼娘共用服务：提供 retrieve_memory、list_open_items、explain_reminder、correct_memory、forget_topic 等受控接口，不让插件直接访问数据库文件。

## 12. 验收标准

- 语义场景：快递多通知合并；会议改期撤销旧提醒；已回复不再建议回复；广告不转为确定账单；模糊时间不自动设准时提醒；通知截断不编造缺失内容。
- 记忆场景：用户纠正覆盖旧推断；删除后旧事件不重新生成；新证据与旧事实冲突可追溯；恢复备份不复活删除事项。
- 后台场景：断网、模型超时、预算耗尽、进程重启、撤权、时区变化和低存储均有可观察状态；不重复入库或通知。
- 规模场景：1 万、10 万、100 万条事件分别记录导入、分页、检索、归档耗时与空间；不把固定条数阈值作为停止保存理由，不将全库加载进内存。
- 质量指标：分别统计事实准确率、事项误报/漏报、提醒有效率、用户纠正率、每日打扰量及成本。先用至少 100 组人工标注样例建立基线；没有真实用户反馈前不宣称“已经懂你”。
- 实机场景：Magic6 与 AYANEO 分别记录后台恢复、提醒到达、推理延迟和耗电；自动化测试不能代替长期实机结论。

本设计替代“固定条数 JSON + 规则摘要”作为长期方向。已有规则和旧数据先用于迁移及回退，不能通过移除数组上限就宣称新版长期记忆已经完成。
## 13. 开源项目调研与选型补充（2026-10-30）

本节基于官方仓库、源码及文档的静态调研；没有安装这些项目或在 Magic6 上做性能实测。以下“采用”均为设计决策，不代表已经集成。来源使用滚动分支，正式引入前必须固定 commit、核验该版本 LICENSE 和传递依赖。

|---|---|---|

| [Graphiti](https://github.com/getzep/graphiti) | 时序知识图谱及持续更新的关系 | 借鉴事实有效时间与变化历史；手机首版用关系表实现必要关系，不立即部署完整图数据库 |

| [Cognee](https://github.com/topoteretes/cognee) | 数据进入记忆的流水线及图/向量检索 | 作为复杂资料导入的候选对照；避免第一版并存多套存储和推理流水线 |

## 14. 从参考机制落到具体模块

### 14.1 组件职责与唯一数据所有者

- EventIngestor：通知、授权可见内容、使用事件和导入资料统一进入事件库。每个来源返回 coverage=complete/partial/unavailable，不能把没看到消息当成事情没发生。
- UnderstandingQueue：保存待处理版本、水位和重试状态，不依赖 WebView 存活。
- EvidenceRetriever：按实体、时间和文本召回；后续可叠加向量检索，统一去重并返回证据 ID。
- SemanticInterpreter：只生成结构化变更提案，不直接写数据库、发通知或调用手机操作。
- MemoryReducer：校验证据、版本、删除标记和冲突；事务写入记忆、事项及 outbox。
- ReflectionPlanner：对有变化的主题重新归纳，产生“待关注事项”和建议候选。
- AttentionPolicy：决定提醒渠道、时机、冷却及静默原因；复用 App 原有提醒调度。
- MemoryGateway：给 Harness、悬浮对话和设置统一接口。App 数据库是默认模式唯一权威库，外部后端的索引和摘要均为可重建派生数据。

“主动理解”和“行动授权”分开：模型可自动记录、关联、给出建议；外部消息中的指令不能变成工具调用权限。引用内容始终作为数据处理，不能覆盖系统约束。来源可能包含恶意指令，验收样例必须包含此类内容。

### 14.2 最小数据模型

| 表 | 关键字段与约束 |
|---|---|
| events | id、source、source_key、revision、occurred_at、received_at、timezone、content_ref、coverage；来源键+修订唯一 |
| entities / entity_aliases | 内部 ID、来源限定标识、别名与证据；不同 App 同名默认不自动合并 |
| claims | id、subject、predicate、value、valid_from/to、recorded_at、status、revision；区分事情何时有效与助手何时获知 |
| evidence_links | event/claim/item 的有向依赖、原文范围、输入版本；支持撤销传播 |
| observations | 主题摘要、supporting_ids、counterevidence_ids、revision、last_reflected_at |
| items | 稳定事项 ID、状态、deadline、timezone、deadline_precision、source_revision、supersedes |
| jobs | input_hash、pipeline_version、permission_epoch、state、attempt、lease_until、checkpoint |
| notification_outbox | item_id、item_revision、channel、due_at、delivery_state；事项版本+提醒阶段唯一 |
| feedback / tombstones | 纠正、撤回、禁止再次生成的作用域；尽量不保存被删除原文 |
| retrieval_index | 派生索引版本及水位；可重建，不作为唯一记忆载体 |

迁移时保留旧 ID 到新 ID 的映射，分批事务导入，校验数量与内容摘要后切换读入口。失败维持旧读入口；不要同时双写两套“权威记忆”。

### 14.3 模型输入输出契约

输入包含当前时间/时区、有限的新事件、相关历史、来源完整性、用户纠正和已有事项版本。模型输出 schema_version、claims、observations、item_changes、suggestions，每个变更必须有 evidence_ids；时间有原文与解析结果，未知值用 null，不能补造日期。

处理流程：

1. 根据新事件关联主题，召回相关历史。
2. 模型提取事实及事项变更提案。
3. 校验引用 ID 必须属于本次实际提供的证据；核对摘录与时间。
4. 通过 revision 乐观锁检查输入是否已过期。新通知改期、用户纠正或撤权时，旧结果丢弃并重新排队。
5. 一个事务写入变更、处理水位及提醒 outbox。
6. 通知发送前再次检查事项版本、取消状态与静默时间。

单次输入/输出预算限制是运行资源保护，不是记忆容量上限。超长事件按段处理，必须保留跨段关系和截断标识。模型格式错误最多一次修复尝试，再失败进入可观察的失败队列，不靠无限重试消耗费用。

## 15. 三种后台节奏与主动建议

以下参数为待验证初值，不是性能承诺：

- 新事件理解：同一来源短时间合并，建议 30–90 秒防抖；可执行时处理一个有界批次，积压留存。紧迫事项可提高优先级，但不能保证系统立即调度。
- 主题反思：仅对证据变化的主题执行，例如“当前行程”“待回复事项”“最近偏好”；先检索再推理，最多两轮补充检索，避免无界 agent 循环。
- 日常归纳：充电等适宜条件下低频整理；没有新证据就跳过。产物是可追溯的主题摘要，不能循环把模型旧推断当成新的独立证据。

Android 周期 WorkManager 最短间隔为 15 分钟，并可能因系统省电而延后。因此防抖窗口只是目标，不能用周期任务承诺每分钟理解；使用事件触发的持久一次性任务，周期任务负责补漏。已有明确时间的提醒走提醒调度，不等下一次模型推理。[官方说明](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)

提醒候选需具备：具体受益、当前证据、未完成状态、合适时间、未重复提醒。信息不足则降低为建议，不发布确定性判断。例如“可能需要确认出发时间”，不能编造实时路况；旅行时间判断需要实际可用的日历/路线等来源。

通知消失、用户没回复鲸鱼娘、App 使用次数变化均不能单独证明事项完成。主动提醒依次提供“知道了 / 稍后 / 已完成 / 判断不对”，反馈改变事项或策略，不自动推断用户人格。

## 16. 容量、性能与部署方案细化

默认端内数据库 + 用户所配置模型 API；后台不启动 PRoot。未来可配置自托管语义服务，但必须明确发送哪些内容、保留多久、如何删除；端内删除先立即生效，外部删除失败显示待同步。

“不限条数”具体含义：
- 不再因为超过固定记录数覆盖最旧记忆；
- 列表游标分页，索引增量更新，摘要只替代检索上下文，不自动替代原始记录；
- 原始事件保留策略与长期事实分开。默认不静默清除长期事实；用户可选择原始资料归档或保留周期；
- 自动归档后仍可检索来源；若原文已按用户策略删除，明确标记证据只剩摘要，降低可验证性；
- 存储紧张时暂停新增并提示，不无限写到系统不可用；
- 向量索引不预先选定：先测试中文实体/时间/全文召回基线，再用向量方案比较准确率、内存、包体和耗电。

## 17. 开发前先做的验证实验

用相同的脱敏或合成中文数据集比较三条路线：现有规则基线、本设计结构化模型流水线、Hindsight 服务适配器。Mem0 可作为记忆更新的补充基线，不同时引入所有框架。

至少覆盖 100 个完整事件序列，而非孤立句子；训练/调提示样本与保留测试集分开：
- 会议创建→改期→取消；
- 快递通知重复→领取→旧通知再次出现；
- 同名联系人跨应用碰撞；
- “明天”“下周”遇到延迟到达、跨午夜及时区变化；
- 新事实推翻旧偏好；
- 用户删除→后台旧请求返回→重启→备份恢复；
- 截断通知、广告伪装紧迫事项、来源中的恶意指令；
- 漏采或撤权，确保不假装拥有完整信息。

分别评估事实准确率、事项 precision/recall、错误提醒率、撤销传播成功率、证据覆盖率、token 消耗和任务延迟。关键确定性测试要求：删除后不复活、取消后不发旧提醒、无证据引用拒绝入库、重试不重复推送。模型质量阈值根据人工标注基线制定，不提前宣称达标。

实机再比较关闭功能与开启功能各自的 24 小时电量/后台行为；同网络与近似使用条件重复测量。Magic6 尚未连接，不能用 AYANEO 的结果替代荣耀后台策略验证。

落地关口：先通过数据库恢复/撤销一致性和语义对照实验，再开放自动提醒；先在影子模式记录“本来会提醒什么”供评估，验证后默认自动处理普通记忆，不要求用户逐条审核。影子模式是开发验证步骤，不是最终用户使用门槛。

## 19. 统一来源协议与增量同步

每个连接器实现 capability、authorize、sync(cursor)、pause、revoke；能力描述声明 supports_backfill、supports_delete_events、coverage、所需权限及来源刷新延迟。插件只能提交规定结构的事件，不能任意写记忆库或绕过发送权限。

事件信封增加：
- connector_id、account_scope、source_record_id、revision、operation(upsert/delete)；
- event_time、observed_time、原始时区、content_hash、content_type；
- permission_epoch、coverage_window、completeness、capture_method；
- provenance_root、parent_event_ids、transformation_version；
- sensitivity、local_only、retention_policy。

同步规则：
1. 先将一页事件与新游标原子提交，再启动解析；任务重跑不跳过尚未保存的页。
2. 游标过期则有界回补并重叠去重，不直接认定缺失记录已删除。
3. 只有权威删除事件或成功完整扫描的既定范围可以判定来源删除；权限失败、超时、网络断开不能清库。
4. 通知、页面和导入文件可能是同一信息的多份表现。保留各自来源，建立同源关系，不能把三个副本当作三份独立证据提高置信度。
5. 未知覆盖、截断、离线时间段进入 coverage_gaps 表。模型必须能知道“可能漏采”，不能推断“你没有回复”。
6. 外部数据附带的提示词按不可信数据处理；链接内容不自动拥有执行动作或读取其他来源的权限。

一次性来源授权后，在授权范围内自动处理，不要求逐条确认记忆。系统授权不能静默代办。来源本地采集和向模型发送分别配置；已有通知允许采集，不等于允许把所有图片或健康数据发送云端。

高吞吐来源先轻量去重/结构解析，再排队模型理解。新到的近期事项优先于历史导入，但历史队列有公平份额，不可永久饿死。主线程不执行 OCR、文件读取或模型请求；并发与批量按设备实测确定。

## 20. 完整压缩机制：原文、证据、摘要和上下文分离

### 20.1 四种压缩各自解决什么

| 层级 | 处理 | 不允许丢失的内容 |
|---|---|---|
| 原始对象层 | 分块无损压缩，内容寻址去重；图片/音频已压缩格式避免无效二次压缩 | 原始字节及来源元数据；去重对象引用计数 |
| 事件层 | 重复通知折叠、页面差异保存、按事项合并经历 | 版本变化、首次/最后出现时间、删除和取消记录 |
| 语义层 | 事件摘要→主题观察，按新证据更新 | 日期、金额、否定、例外、责任主体、用户纠正、证据依赖 |
| 模型上下文层 | 检索相关摘要和事实，按需要展开证据 | 当前任务必需的精确细节与来源不确定性 |

长期记录不设产品级条数上限；单次输入、输出、导入批量和任务耗时仍有资源上限。摘要不能冒充原文。图片 OCR、音频转写属于有损解释，文本压缩率再高也不能把它们当成原始证据的等价替代。

### 20.2 可追溯结构与压缩事务

新增 raw_objects、summary_versions、summary_dependencies、archive_segments、compression_jobs：
- raw_objects 记录 hash、codec/version、原始长度、压缩长度、校验值、加密信息、引用计数；
- summary_versions 保存主题、覆盖时间、输入版本集合、保护字段、摘要文本、质量状态；
- summary_dependencies 建立摘要→事实→事件→原始对象依赖；
- archive_segments 保存可定位清单与索引，不把全部历史塞进单个必须整体解压的大文件；
- compression_jobs 记录水位、租约和恢复进度。

流程：生成候选→字段/证据校验→写新对象并校验解压→事务切换引用→后续回收旧冗余对象。断电或空间不足时保持旧对象可读。临时文件空间也计入预算；压缩比不佳时保留原格式。

用户删除的对象不能仅改为“归档”。依赖摘要立即停止检索并重建，索引和缓存同步失效；共享原始对象在仍有有效引用时保留，但删除作用域不得再检索到它。用户要求全局忘记时传播到所有对应引用，备份恢复应用删除标记。

### 20.3 语义压缩的保护与重建

建立保护字段集合：未完成事项、明确承诺、金额/单位、时间/时区、取件或预约所需短期信息、用户明确纠正、矛盾与否定。短期凭证只在必要期间本地保存，不作为长期偏好或泛化画像材料。

摘要必须说明时间覆盖和未知部分。摘要更新优先读取结构化事实、新证据及受影响旧原文，不能只把上版摘要再摘要。周期性抽样从原文复核；发现失真则回退摘要版本并重建。

原文默认不因语义压缩自动删除。用户另选保留周期后，删除前检查未完成事项所依赖的必要证据，明确解释保留例外；没有原文的摘要标记 source_unavailable，不能继续呈现“可核对原文”。授权撤回与立即忘记优先于保留例外。

### 20.4 检索与展开

先检索时间、实体、结构化事项和全文摘要，必要时叠加向量召回；再按问题展开相关原始片段。问“最近要做什么”优先事项状态；问“当时具体说了什么”必须查原文，只有摘要时说明无法提供原话。

模型预算不足则分段取证，不以截断保护字段解决。失效摘要、已删除证据、权限不允许发送的内容在检索与出站前双重过滤。

## 21. 采集与压缩共同验收的场景

1. 邮件通知、分享截图和日历指向同一次预约：关联一件事项，保留三种来源；截图 OCR 的时间错误不能覆盖权威日历的新版本。
2. 多日上百条物流通知：按包裹保留关键状态迁移，近期未领取事项仍能精确读取领取信息；领取后取消提醒。
3. 长文及音频：按页/时间码切分、摘要关联原始片段；数字、否定句和人物归属单独核对。
4. 来源撤权时模型正在处理：permission_epoch 失配拒绝提交；压缩任务不得绕过撤权继续上传。
5. 文件移走、Provider 暂时离线、账号失效：分别显示状态，不误判为用户要求忘记。
6. 删除原文后恢复旧备份：删除标记先应用，摘要和向量不能复活。
7. 压缩中断、损坏、磁盘不足：旧数据仍可读，校验失败隔离，有恢复入口。
8. 百万级事件库：报告每来源占用、真实压缩比、摘要字段保留率、检索正确率、展开 P50/P95、峰值内存和耗电；不预设一定压到某个比例。

设置页面统一增加“信息来源”与“存储与压缩”：每来源显示授权、覆盖范围、最后采集/理解时间、积压、发送范围、占用及停止/删除入口。存储页分别显示原始资料、事实、摘要、索引、临时文件，避免只显示一个无法解释的总容量。

开发顺序：先统一现有来源协议和数据库→加入无损归档与恢复→接入分享/指定资料同步→语义压缩与证据展开→可见页面/多媒体→逐个账号连接器→可选位置健康。每新增来源都跑同一套撤权、重复、删除、压缩回查测试，避免扩充信息种类同时引入新的孤立记忆系统。
