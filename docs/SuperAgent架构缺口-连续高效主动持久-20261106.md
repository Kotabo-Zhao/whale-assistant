# 鲸鱼助手：连续、高效、主动、持久的架构对照

核对日期：2026-11-06。对象：鲸鱼助手 preview.76 工作树，以及 DeepSeek 公开的 dsh-superagent-prototype。本文区分已实现机制、已有验收、这轮发现和后续建议；后续建议尚未开发。

## 总体判断

现有系统已经具备 Agent 的关键骨架：目标与工单、依赖、独立 Worker、主动事件、回执、预算、独立监督和恢复。距离可靠的长期助手，主要差距在于这些机制之间的状态一致性、持续协调和可验证执行，而不是继续增加工具数量。

这轮屏控暴露了典型问题：本地动作可以很快完成，主模型却仍会补做观察、截图，评分器还可能误读控制浮层导致返工。因此“工具调用快”“任务已完成”“用户及时得到回复”必须分别测量。

| 目标 | 当前已有 | 关键缺口 | 用户可感知的后果 |
| --- | --- | --- | --- |
| 连续 | 工单续接、依赖、目标条件和证据指纹；新回执能唤醒协调会话 | 跨组件的统一任务生命周期；后台命令、Worker、用户追问的明确占槽与交接规则；持续重规划的端到端验收 | 单项任务完成后，整个目标未必继续推进；繁忙时追问可能延迟 |
| 高效 | 原始帧 OCR、常驻输入、动作与观察合并、资源感知并发、有限连续导航 | 主会话工具与上下文按任务裁剪；交互时延预算；评分、视觉、执行的证据复用 | 简单操作仍携带大量上下文，额外模型回合拖慢收尾 |
| 主动 | 新对话和资料更新触发、版本去重、安静时段、候选暂存、事项关联 | 长期目标与跨资料的检索；事项生命周期和反馈；候选价值与打扰成本的可评估机制 | 能发起话题，但容易漏掉长期关联，难稳定判断“现在值得打扰” |
| 持久 | 状态落盘、校验与备份、坏记录隔离、独立看门狗、恢复确认 | 领域状态、Worker、目标、回执之间的事务一致性；动作结果未知后的对账；长时间系统级故障验收 | 中断后可能恢复局部状态，仍需辨认哪些动作实际发生过 |

## 1. 连续：从“能恢复一个任务”到“持续推进一个目标”

上游对 Ticket、Assignment、Executor Session、Input 的生命周期有明确区分。已送达输入和已读输入分别记录；后台工作尚未结束时保持工作槽；交给人处理时释放槽；重启保留尚未读入会话的输入。它还为人的消息或状态请求保留额外槽，并优先唤醒已有任务，避免新任务挤压追问。

本项目 `workers.js` / `worker-goals.js` 已有依赖、目标完成条件、预算、成员修订与证据指纹失效，不能再列为“缺少目标机制”。不足在于协调仍依赖主会话被唤醒后读状态、判断和操作，尚未证明所有故障和后台工作情形都具有与上游相当的交接语义。

建议补齐：

1. 为“收到输入 → 分派 → 执行 → 报告 → 核验 → 交接”统一记录版本和关联标识。明确收到、已送达、已读、已回应的区别，禁止只凭消息发出就视为处理完成。
2. 把目标协调作为持久角色：前置证据变更只使受影响分支失效，保留仍有效结果；失败后决定重试、替代路径或请求信息。已有预算不允许被协调器自行抬高。
3. 明确前台用户追问的优先级、设备互斥和后台命令占槽规则；用负载测试证明用户能及时暂停、追问与续接。
4. 连续屏控保持有界：本版仅支持同一已知 App 内 1–6 个文字导航目标。未知页面、跨 App、敏感操作需要重新观察和确认；不能将其描述为已拥有任意长任务执行器。

验收：前置任务被修改、途中到来用户追问、后台命令仍在运行、主会话重启这四类情况下，目标不丢失、不重复创建任务、不使用过期证据，用户消息不会被新任务长期挤占。

## 2. 高效：减少模型决策次数，并让证据只处理一次

本版新增本地连续导航，减少每次点击后的模型往返；每步重新读取页面、核实前台应用，缺失和歧义时停止。动作并未简化为盲放坐标脚本。实际测量见[真实 App 多步屏控实测](真实App多步屏控实测-20261106.md)。

仍有三层缺口：

- **主会话上下文过大。** 本轮新会话首轮输入量在约 3 万 token 量级（含缓存部分；不同服务的 usage 口径需注明）。Worker 有模式工具白名单，主会话尚不能为一个简单手机导航请求稳定裁剪成最小工具集。应按能力路由工具，复用前缀缓存，减少无关资料和提示；不能偷偷更换用户配置的模型。
- **缺少交互时延预算。** 已有任务与目标 token / 调用 / 时间预算，但分钟级任务预算不足以约束秒级交互。应分别观测排队、首 token、模型生成、工具、页面稳定、核验及评分的耗时，按任务类型报告中位数和长尾，不能只测点击注入的毫秒数。
- **执行与核验没有充分共享证据。** 本轮遇到控制浮层被误认为目标 App 的“暂停 / 停止”，导致评分返工；还遇到转场帧被当成最终页。修复应保留来源、时间、画面范围和不确定性，让后续核验复用同一证据。稳定画面并不自动证明支付、发送或保存成功。

后续优化应优先做最小工具上下文、任务级证据缓存和受控的轻量核验。模型再看一次只应解决真实疑问；不能靠关闭评分、隐瞒失败或无限减少等待来制造速度数字。

验收：相同真实 App 路径、相同模型配置、多次独立会话对比。分别统计最后页面到达和整轮结束；保留慢样本与失败，记录主模型回合、工具数及 reviewer 返工数。建议初始工程目标为简单已知路径最多两次主模型调用；时延目标需在更多网络样本后确定，不能把本轮小样本当作 p95 保证。

## 3. 主动：已经事件触发，接下来提升判断价值

当前 `ContextFollowupEvents.kt` 会在对话或资料变更时写入版本化待处理事件；扫描仅消费实际读到的版本。展示有安静时段、锁屏、忙碌与冷却约束，判断不再是每天一次。已有考虑过的签名、稳定事项标识、相似事项去重、展示 / 回复事件及 `matterForTask` 工单关联。

主要限制是证据选择比较窄：`PetContextFollowup.kt` 面向最近一周的对话，截取最后四条消息、每条最多 400 字，用最多两个近期用户查询做词面检索，再选择一份匹配资料的片段。该设计节省资源，但对跨项目、长时间跨度和多个资料共同指向的机会不够敏感。

建议补齐：

1. 结合事件增量与长期目标索引检索，区分事实、用户偏好、承诺、期限和待确认事项；保留资料版本及引用，删除或修订后撤回过期候选。
2. 事项具有明确的待考虑、可提出、已提出、稍后、无需再提、已完成状态。去重结合事项身份和证据变化，避免只依赖标题相似；真正新增进展应允许再次跟进。
3. 排序同时考虑可行动性、新信息、用户当前任务、置信度与打扰成本。“有更新”触发判断，“值得讨论”才通知，默认不自动扩大执行授权。
4. 用接受率、无效打扰率、重复率、过期引用率和跟进完成率评估；目前没有足够证据声称主动判断已达到稳定质量。

验收：改写同一事项不重复提醒；用户表示无需再提后停止；新证据改变决定时能再次提出；与近期对话不相邻但与长期目标有关的资料能被检索；关闭主动能力后在途结果不会冒出。

## 4. 持久：统一事实记录，并能解释“结果未知”

上游 [Store](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/src/app/store.ts) 用 SQLite 管理领域仓库、配置版本、回执和键值状态，启用 WAL 与 synchronous FULL；宿主先锁定状态目录，再打开数据库并迁移。

当前 `superagent-domain.js` 将领域仓库、effects、messages、coordinators、matters 放在同一 `domain.json` 快照内，已有内存回滚、落盘后改名和未变化时跳写，不能说它没有原子保存。缺口是这份快照与 Worker 记录、goal 文件、Android 主动事件及收件箱仍不是同一事务。单份文件原子写入无法自动保证多个组件共同提交。

另外，资料 / 记忆已经有 SQLite 权威存储迁移路径（`CompanionMemoryStore` / `UnifiedUnderstandingStore`），不能把所有数据笼统归为 JSON。迁移目标应聚焦执行事实和跨组件一致性，不应再次推倒已完成的资料库。

建议补齐：

1. 在本机建立统一执行日志，以事务记录输入、决定、执行尝试、回执和待投递消息。由一个拥有者写入，Android 与 guest 通过受控接口交互，避免两个进程各自宣称成功。
2. 持久化 operationId 与执行代次，区分未执行、执行中、确认完成、结果未知。屏幕操作的外部副作用不能承诺 exactly-once；进程在点击后被杀，应先重读目标状态对账，禁止自动从头重放。本版序列取消票据和观察租约仍是进程内机制。
3. 原生监督继续独立于 Node。现有监督、坏记录隔离、备份恢复和失败写入回滚有效，但还需对存储耗尽、迁移中断、整机重启、长时间 Doze、网络来回切换和动作后立即杀进程做专项验证。
4. 设计可量化的数据保留与空间预算、备份验证、兼容升级及回退。恢复界面应展示证据和不确定部分，而不是将“能启动”写成“任务已恢复”。

验收：在每个持久化边界注入中断，恢复后没有孤立任务、静默丢输入或重复投递；动作已发生而回执未提交时进入对账；备份损坏与磁盘满不扩大为全队列丢失。随后做至少一轮完整昼夜待机 / 恢复测试，并测量后台耗电与内存走势。

## 建议开发顺序

| 顺序 | 工作包 | 可交付结果 |
| --- | --- | --- |
| P0 | 执行日志与结果未知对账 | 打通领域、工单、目标和回执的一致性，先覆盖真实手机操作的断点 |
| P1 | 主会话最小上下文与交互计时 | 减少简单操作的模型回合，建立可回归的真实 App 基准和慢调用诊断 |
| P1 | 目标协调及用户追问优先级 | 多任务长期目标可持续推进，忙碌时仍可及时控制和续接 |
| P2 | 主动事项生命周期与长期检索 | 对重复、稍后、完成和新证据形成明确闭环，衡量主动质量 |
| 贯穿上述阶段 | 系统级故障与昼夜验收 | 每项机制有真实设备证据；后续再安排获准渠道的端到端续接 |

不建议用“距完整 SuperAgent 还差百分之多少”表示进度。以一个真实长期目标在新消息、失败、重启和证据变更下仍能正确推进为验收单位，才能同时检验连续、高效、主动和持久。

## preview.77 的增量与仍然存在的缺口

主屏操作已建立 Android SQLite 执行事实：稳定操作编号、写前意图、注入与观察阶段、持久取消、回执接收、旧代次隔离及 unknown 对账。真实点击后回执提交失败，再杀 App 重启，已验证不会重复点击。桌宠表达真实控制状态，接入可即时暂停与停止的菜单。详见本日[执行恢复验收](桌宠状态与执行恢复实测-20261106.md)。

这完成了 P0 中“真实手机操作断点”的第一段。领域快照、Worker、goal、主动事项与用户收件箱仍各自保存；尚没有跨组件事务或统一待投递表。原始 Shell 与副屏也尚未全部经过该日志，不能将主屏工具的保护扩大解释为全系统 exactly-once。

效率验收开始使用三 App 的资料阅读、文档编辑与整理任务。首轮暴露中文输入法改写逐键输入、模型在地址栏重复尝试的问题；补充了原样粘贴和同屏重复输入拦截。局部连续导航的两秒级成绩不代表复杂任务已稳定快速，后续应按完整任务完成率、模型回合数、修复次数与总耗时评估。

本轮复杂任务最终产物经独立核验完成，但不是一次自主通过：长会话产生 15 秒观察凭据过期循环，模型漏掉中文句号仍声称完成，最后的续接转用了未纳入执行日志的原始 Shell 点击。压缩上下文后调用间隔下降，但仍需要人工发出纠错与压缩指令。下一阶段应优先补：有当前页面与任务验收条件的精简执行上下文、执行前重新定位的语义动作、所有设备输入统一经过日志，以及由持久目标监督预算和完成核验。详见[复杂操控实测](复杂手机操控实测-20261106.md)。

下一步仍是跨组件提交与待投递一致性、目标协调与追问优先级、长期检索及主动事项反馈闭环，以及真实存储耗尽、整机重启和昼夜待机验收。跨渠道续接继续按用户要求暂缓。
