2. 它如何把一句话变成长期任务

外部 Source → 不可变 Trigger → Thread
                          ↓ 收取范围、身份与授权 gate
                    Eval → Decision
                          ↓ 接受
                  Ticket + Mandate
                          ↓
                     Assignment → Harness Session / Executor
                          ↓
                   Report / Attention → Outbox → 原始 Channel
对象准确职责不能混为一谈的对象
Trigger记录消息来源、作者、是否人类、时间、所属线程、原文、回复目标；按 ID 去重不是模型生成的任务摘要
Thread组织会话、订阅和待判断消息；同一线程同时一个 Eval不等于单个任务；一个线程可关联多个 Ticket
Eval / Decision一次判断及其结论，携带规则、理由、授权版本等审计信息不是永远有效的分类标签
Ticket跨回合、跨重启存在的工作记录不等于 Harness Session；会话消失不必删除任务
Mandate接受时的授权依据与范围；恢复时重新核对当前策略不等于操作系统沙箱权限，也不是一份万能授权令牌
Assignment一次具体执行尝试；可被中断、重建，保留历史不等于整个 Ticket 的寿命
Report / Attention工作进度/结论，以及需要人的具体问题不是靠回复里有没有问号猜等待状态

源码：model.ts、intake.ts。

3. 路由智能：语义判断与确定性约束各管什么

原型不是用一组关键词判断聊天/执行。Source 先定义哪些事件会被接收；Policy 判断身份、提及方式、来源及主动工作模式；模型再结合上下文判断任务去向或主动规则是否成立。代码校验模型输出是否满足授权条件，但不能证明模型对语义的理解一定正确。

  • off / observe / auto 约束推断出来的主动工作；显式获准的请求不因 observe 而一律拒绝。
  • 主动接受必须覆盖每个启用规则一次，不能漏评或重复；还需要 direction 检查及非空 intent_evidence。有 evidence 字段不等于引用真实，仍需质量评测。
  • 机器人消息不能取得与人类显式指令相同的权限；配置内的 bot 可以作为 inferred 候选，不是“所有 bot 都忽略”。
  • 相关线程仅提供上下文。订阅、相关性和授权是三个不同概念；不能因为读到文件中的一句命令就视为用户新指令。
  • 已经被一个任务接手的人类追问优先交还原执行者。主路由不能在原执行者仍持有它时重复接受、改派或忽略；停止操作例外。超出范围由执行者 handback，每个任务对同一消息只能交回一次，所有持有者释放后才能重新评估。

这直接对应鲸鱼助手“查本地资料被当成闲聊”“简短回答丢任务”的问题：不能只增加分类 prompt；必须知道当前有没有未回答的问题、正在执行的任务以及这条消息回复谁。当前 PetIntentRouter.kt 是独立 HTTP 三分类，最近 6 条上下文、temperature=0、max_tokens=80、读取超时 60 秒；它不是关键词兜底，但仍会语义误判，而且每轮额外串行请求会增加首字延迟。

源码：policy.ts、assessment.ts、evals.ts。

4. 超时、重复判断与过期结果

Eval 的计时从候选实际投递到判断会话开始，而非进入队列时开始。暂停期间顺延 deadline。超时后重新排队两次，第三次记 unavailable。结果携带 evalId 时，旧 Eval 的结果会被拒绝；同一 Trigger 已经创建过 Ticket 时，重复接受返回已有 Decision，不再建第二个任务。策略版本变化会重新开始正在进行的 Eval。

这些不是多余防御：它们分别解决排队被误判超时、暂停消耗时限、模型迟到响应写入新任务、重试导致重复任务。手机实现也不必照搬全部 Eval 机制，但至少需要 requestId/turnId 关联，避免把上一轮完成当成本轮完成。

5. 授权与权限：最容易误读的边界

原型的 Mandate 是任务治理机制。执行器默认以操作者 OS 用户身份执行命令，无逐次审批；worktree 隔离是工作目录隔离，不是安全沙箱。限制部分工具不代表有了文件系统隔离；worker 仍有 shell。主路由“不读代码”主要是提示词规则，它实际仍有 read/bash 等工具。执行说明、工具与 Session 装配

策略收紧时，Tickets.policyChanged 给活跃任务加 policy-changed 输入；执行 prompt 允许在原范围内处理已开始的工作。这不等于即时取消。显式 stop 则结束任务、撤回其授权，不能被普通后续消息偷偷恢复。

手机应区分“关闭主动建议”“停止一个任务”“撤销资料访问”“调整下一次会话的权限”。后三者不能都只发一条提示给模型。特别是资料权限撤销，应由实际读取工具检查当前授权；已发给模型的数据无法通过后续撤销逆向收回。

鲸鱼助手已能通过真实 /permission 命令设置桌宠委派会话；当前 preset 参与 scope，变更后下一次任务切换会话。不能把这一行为描述成已经取消现有后台操作。显式接续主会话还保留原会话权限，应在 UI 中明确当前生效值。

6. 追问、完成与失败：状态如何驱动 UI

WorkerReport.question 三态明确：字符串提出问题，null 清除，省略保留旧问题；ready 会清除问题，ready 与新问题不能同时提交。askedBy 必须指向已到达该任务的真实人类消息；答案也必须关联可回答的触发消息。问题换掉时撤回尚未发送的旧问题。

面板状态由事实按固定顺序推导：ended → delivery failure → attention → ready/review → blocked/failed 等待人 → queued → idle → working。“模型 turn 已结束”不意味着任务完成，“ready”也可能在等待相关 PR 结束。来源：assignments.ts、stage.ts。

鲸鱼助手现在看到 ask_user_question 只提取前三条问题文本；审批事件只显示转主界面的提示。桌宠输入仍受 busy 控制。缺少持久化 questionId、选项、答复关联及本地直接提交。借鉴 Attention 的意义是让 UI 知道该显示“回答问题”还是“等待执行”，而非把一段提示再包装成卡片就结束。

7. 可靠性逐层拆开，不能统称 exactly-once

层实际机制保证范围与剩余边界
数据库SQLite WAL、synchronous=FULL；Engine 命令事务；afterCommit 才触发后续动作本地事务一致性，不覆盖远端 HTTP 或 shell 的外部效果
Effects(kind,key) 合并，seq 保序，generation 标识更新；完成时按 seq+generation 删除旧执行完成不会删掉新 payload；崩溃后可重试，handler 必须允许重入
暂时等待Later 只推迟 due，不增加失败次数暂停/缺少 Source 与实际故障分开
真实失败指数退避；默认 2 秒到 60 秒；3 次起 health 显示 error3 次是健康告警阈值，不是所有 effect 都永久停止重试
会话消息requestId 形成稳定 messageId；检查 live events、nextTurn/nextStep inbox、已落盘历史；投递后 flush 再确认防同一个请求反复投递；投递成功仍不等于模型已经读取
Outboxreceipt 与 reply effect 原子入库；串行发送；同任务/频道前序消息优先前序失败达到阈值后允许后续通过，不是无限期严格 FIFO
GitHub发送前扫描同账户评论中的 messageId HTML 标记，再 POST能协调不确定发送结果；不是服务端原子幂等键，依赖标记可读且保留、单运行实例等条件
飞书每次重试沿用 --idempotency-key message.id服务端具体幂等时效及 CLI 行为需外部验证；本次只测代码传参
任意工具操作恢复提示要求检查 worktree/git/远端状态再继续不是给删除、发送、支付等任意操作自动提供幂等性

Outbox 的外部 send 与本地 settle 之间存在崩溃窗口，但不能据此断言“必然重复”，因为具体 Channel 已实现不同的协调机制。更准确的说法是：持久化重试，加业务级去重/协调；没有覆盖所有副作用的分布式事务。

源码：effects、delivery、outbox、GitHub channel、飞书 channel。

8. 重启恢复与并发调度

原型明确区分 inputsDelivered 与 inputsRead：消息放入 inbox 只是投递，实际被步骤取入历史后才算读取。中断时未读输入可重新交给下一 Assignment。已有 waiting/ready/blocked/failed 报告且没有更晚投递时保留 settled 状态；否则新建执行尝试并加入恢复说明。

执行槽统计启动中、准备中、运行及相关后台任务；普通并发上限之外保留一个人类消息/状态请求槽。准备命令最长 10 分钟；worker 的前台 shell 5 秒转后台；回合后后台作业上限 30 分钟；关闭时最多等待 10 秒清理。30 分钟边界不会保证所有子 Agent 一律消失。交给人处理后可释放槽并保留部分服务作业。

不能简单把这些常数复制到 Android：并行 PRoot/Node 会话、BGE 推理、内存和温控的真实代价尚未测量。手机建议从一个执行任务开始，用户追问直接进入该任务，避免为闲聊再启动多个工作会话。

源码及针对竞态的测试：dsh.ts、runtime-concurrency.spec.ts。注意：生命周期回调多处携带 assignmentId，而 report 的领域入口按 ticket 取当前 Assignment；不能仅凭类型声称所有迟到 report 都有代际校验，完整故障注入仍是待验证项。

9. DeepSeek 502：它能改善恢复，不能修好服务端

执行器将结构化 status=408、429、≥500 视为可重试；字符串匹配覆盖部分网络错误和 500–504。实际 status 分支没有上界，字符串匹配与数值分支并非完全等价。worker 最多自动继续 3 次，等待 15、30、60 秒，然后转失败；计数保存在进程 Map，不能当成跨重启的全局预算。准备目录失败不自动重试，避免把半成品目录误当准备成功。

恢复是向原会话投递继续执行说明，不是重新发送整个用户任务。鲸鱼助手应分别记录发生在意图分类、直聊请求、Harness 模型调用还是本地桥接；HTTP 502 与 WebSocket 断线不能混报。还要考虑底层 SDK 已经重试，不能叠加多层无限重试。没有真实请求日志、request ID、响应及网络对照，不能说“SuperAgent 已解决 DeepSeek 502”。

10. 上下文、长期记忆与人格不是一回事

原型做得好的是“短预览 + 完整原文的读取指针”。worker assignment 预览 1500 字符、Trigger 600；资源正文默认 4000、最多 8000 UTF-16 单元，列表默认 20、最多 50。主路由有 14 个应用工具，worker 有 6 个应用工具，另加 Harness 工具。worker 的读取 API 有任务范围校验；这不等于 shell 也受相同数据范围隔离。

原型没有在上述任务存储与读取链路里实现 BGE 向量检索、长期人格记忆或 SillyTavern 角色卡系统。src/core/memory.ts 是领域测试用内存仓库，不是 AI 长期记忆算法。不能因为文件名 memory 就把它当成语义记忆方案。

提示词按 shared/role/team/subscription/replies/work/admission/handoff/environment/policy 等部分组合，并保留版本与基线，方便比较默认提示词更新。角色模型只为新会话初始化，不应覆盖已有手动选择。鲸鱼助手可借鉴版本化和实际 prompt 预览，但角色卡兼容性还取决于消息角色、顺序、历史、工具定义、模型参数和输出长度，不能只比较角色卡文本。角色风格、任务授权和工具能力应明确分层。

存储也有明显代价：旧 Trigger、Decision、Ticket、Outbox receipt、设置及 prompt 版本目前不自动删除。TextCache 是 LRU，但总量限制不是硬上限——最新一个超大条目仍会保留；重启后分页缓存丢失，需要从 offset=0 重新读取。架构中的持久化限制、cache.ts

手机应保留用户资料和重要记忆的长久可读性，限制热缓存、预览、单次检索量；不能把“正文存得长”实现为“每次全部塞进模型”。删除资料还要覆盖索引、派生记忆及引用失效。鲸鱼助手已有 SharedMemoryJobs SQLite 队列、组合去重键、租约与恢复，不需要为了学习原型重写这一套。

12. 学什么、保留什么、先不引入什么

顺序最小改动范围理由

15. 仍待核实的细节与判断边界

  • GitHub 不确定写入后的可见性、评论标记被编辑删除、飞书幂等键保留期限：本轮没有真实服务实验。
  • 所有迟到 worker report、运行期策略变化和外部副作用之间的竞态：已有官方测试覆盖若干场景，但不应称穷尽。
  • 长期大量数据下，同步 SQLite FULL 写入、首次扫描 Session 全历史构建去重集合、全文分页缓存的 CPU/IO/内存代价：未压测。
  • 原型的 prompt 规则并不构成 shell 沙箱；手机工具权限必须在自身执行边界落实。
  • 上游 release 与内置 Harness 都属快速变化依赖；移植前应核对实际包版本、协议字段及手机 rootfs 中加载版本，不能只按项目名称认兼容。
  • 本次没有改动产品实现、安装 APK 或推送 Git；只增加可审阅的研究报告与测试记录。

建议落点：先把桌宠做成 Harness 会话的完整、可恢复前端，同时保留角色卡与工具能力；然后把跨回合任务事实存下来。SuperAgent 的价值在于把这些事实明确化，而不是让手机上出现更多 Agent、更多分类层和更多摘要。
