# 预览五十四 · 桌宠在中断后继续接单

桌宠将排队消息的编号一直传到前台请求或后台交办。交办前先保存执行计划，计划包含原任务编号、模式、资料需求和来源会话。若后台已经接取、前台还没保存回执，重启后可在「待处理消息」点击「恢复交办」。恢复会重新检查授权，并用原编号向 SuperAgent 核对工单。

聊天记录、后续消息队列和后台命令先写入临时文件，写入、同步和关闭均成功后才替换原文件。排队消息进入对话时，先保存带原编号的请求，再标为开始回复。重启时会把这两份记录关联到同一个重试入口。

桌宠最多保留 64 条待处理消息。队列已满或写入失败时，输入框保留本次内容。切换话题时可以暂停尚在判断的消息，待处理记录和未提交的草稿可继续使用。已进入本地交办阶段的消息会先保存回执。

## AYANEO 故障验证

| 故障位置 | 操作 | 观察结果 |
| --- | --- | --- |
| 后台已执行、前台尚未保存回执 | 在测试接单函数返回前用 ADB 强制停止整个应用，重新启动测试进程，从桌宠恢复交办 | 主消息和下一条排队消息均保留，两次接取得到同一工单 ID，测试工作只执行一次，恢复后成功接收新单 |
| 写入中途空间不足 | 向临时文件写入半份内容，借助设备内核 `/dev/full` 在写入路径产生 ENOSPC，同时覆盖新增命令和确认命令失败 | 旧队列可读，原命令保留，新输入仍可见，恢复写入后按原编号重试得到一份记录 |
| 前台长时间不回复、分类缓慢 | 连续投放 60 条，65 秒后再投 4 条，并尝试超额投单、结束等待和切换话题 | 已接收的 64 条编号各不相同，旧消息可恢复，桌宠可处理新话题 |
| 旧工单重新投递 | 将隔离队列内 24 条工单的创建时间设为一天前，首次接取后扣留全部确认，再加入 1 条新单，并在新的 Node 进程中重新加载执行账本 | 原 24 个工单 ID 逐一匹配，新旧共 25 个独立工单和 25 条执行记录，后台命令全部确认并清空 |

测试使用 AYANEO 上已安装的 SuperAgent 手机接单模块、实际悬浮窗和本地持久化。测试工作是向隔离文件追加执行记录。结果适用于此次覆盖的任务交办和回执恢复时点。外部服务执行动作后丢失其自身回执时，防重仍取决于该工具的协议。一天的队列年龄通过时间戳模拟。

复测强杀场景可使用 `scripts/test-pet-process-death.ps1`，传入 ADB 路径和设备序列号。脚本等待工单落盘标记后才执行强停，并核对新进程的验证结果。需要先安装本版应用、设备测试包及其运行环境。

应用 0.3.8-preview.54，版本号 99。安装包位于 `build/whale-assistant-0.3.8-preview.54.apk`，AYANEO 安装文件 SHA-256 为 `30d23b7884da36e9f4f0399f647797a48c53db067c86f162bec2145833d9f722`。
